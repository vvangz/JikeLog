# ADR-008 备忘录：提醒、推送与日历

- 状态：已采纳
- 日期：2026-10-10

## 背景

- 需求第 6 条：备忘录包含日期时间和备忘内容，支持提前提醒，并且要与日历关联。
- 需求第 9 条：通知渠道为 App 推送。

实施计划 3.5 节定下了方向：
- 每台设备在本地注册精确闹钟。
- 服务端在提醒时刻检查：设备尚未同步到这条备忘录时，用极光推送补发，避免重复提醒。
- 日历分两部分：App 内的月、周、日程视图，以及可选的单向写入系统日历。

本 ADR 记录实现中的具体决定，包括两处与计划不同的地方。

## 决策

### 1. 数据模型：同步实体 `memo`

| 字段 | 类型 | 加密 | 说明 |
|---|---|---|---|
| `content` | 长文本（可补丁合并），必填，≤5000 字 | 是 | 备忘内容 |
| `at` | 时刻：Unix 毫秒（UTC），2000–2199 年 | 否 | 备忘时间 |
| `allDay` | 0/1 | 否 | 全天备忘 |
| `reminders` | 提前分钟数列表，如 `"0,15,1440"` | 否 | 空串表示不提醒 |
| `done` | 0/1 | 否 | 已完成 |

- **只有内容加密**。服务端要在提醒时刻推送，所以必须能读到时间和提醒设置。这几个字段只透露"某个时间有一条备忘"，不包含用户写的内容。
- **`reminders` 只接受规范形式**：升序、不重复、没有前导零，最多 5 个，每个提前 0 分钟到 30 天。这和用户设置中的"默认提醒"范围一致。各端写出的值逐字相同，字段级合并时不会因为写法不同而误判为冲突。
- **全天备忘的 `at` 取当天本地时间 9:00**，提前提醒从这个时刻往前算。日历上只显示日期。
- 字段级合并沿用 ADR-005，`content` 和工作日志正文一样做补丁合并。举例：一台设备改了时间，另一台改了提醒，两处修改都会保留。

### 2. 提醒以本地闹钟为主，服务端推送补位

- **App 端**：
  - 每次备忘录有变化（本机编辑或同步拉取后），App 按最新数据重新排定本地通知。精确闹钟使用 flutter_local_notifications。
  - 只排定未来最近的 64 条，留在 Android 单个应用 500 个闹钟的上限之内。
  - 重启手机、App 更新后由插件重新排定。
  - 本地通知运行在本机，可以显示备忘内容。
- **服务端**：在提醒时刻，对同一账号的每台设备判断是否需要推送。**同时满足以下两点就不推送**，否则推送：
  1. 设备上报了"能在本地按时提醒"，即已授予通知权限和精确闹钟权限，`devices.local_reminders = true`。
  2. 设备已确认的同步序号不小于这条备忘录的当前序号（`last_ack_seq >= records.server_seq`），说明它已经拿到这一版备忘录，本地闹钟会按时响。
- 有了第 1 点，用户拒绝通知或精确闹钟权限的设备仍然能通过推送收到提醒，不会两头落空。

### 3. 服务端调度用 PostgreSQL 表，不用 asynq（与计划不同）

计划中服务端延时任务用 asynq（基于 Redis）。实现改为 `memo_reminders` 表加一个轮询调度器，原因：

1. **和数据写入在同一事务**。备忘录的每次写入都在同步推送事务里先删除、再重建它的待发提醒。修改时间、修改提醒、标记完成、删除这四种情况都是同一条代码路径。用 asynq 的话，入队发生在事务之外。事务回滚或进程在中途崩溃时，任务和数据会不一致，还需要另外做补偿。
2. **多实例安全**：用 `FOR UPDATE SKIP LOCKED` 领取到期提醒。领取的同时写入 2 分钟的领取期限。发送失败或实例崩溃后，期限一过，任一实例都可以重试，最多尝试 3 次。
3. **不新增组件**：不需要 worker 进程，也不需要 Redis 持久化配置。

细节：
- 每 10 秒检查一次，所以推送最多延后 10 秒。主要提醒由本地闹钟负责，推送只是补位，这个精度足够。
- 服务停机超过 1 小时，期间到期的提醒不再补发，过时的提醒只会打扰用户。
- 发送成功后只删除领取时的那一条（按 `fire_at` 匹配）。如果期间备忘录被修改，提醒已经被替换成新的一条，新的会保留。

### 4. 推送内容不包含备忘内容

推送经过第三方通道，即极光和手机厂商。推送正文只说明时间，例如"今天 15:30 有一条备忘""15:30 的备忘到时间了"。时间按设备上报的时区显示。用户点按通知后进入 App，在本地解密后查看内容。

### 5. 极光推送的接入方式

- **服务端**：`JIKELOG_PUSH_PROVIDER=jpush` 时，调用极光 REST API v3，参数包括：
  - 通知渠道 `memo_reminders`。
  - `classification=1`，即系统消息，厂商通道按重要通知下发。
  - 离线保留 1 小时。

  默认值为 `log`，只在日志中记录推送设备数，不记录内容。没有开通极光的环境（开发、验收）提醒完全依赖本地闹钟。
- **App 端**：
  - 极光 AppKey 由构建参数注入：环境变量 `JPUSH_APPKEY` 写入 Android 清单，`--dart-define=JIKELOG_JPUSH_APPKEY` 注入 Dart 代码。为空时 App 不初始化推送，也不上报推送标识。
  - 用户同意隐私政策之后，App 才依次调用 `setAuth(true)` 和 `setup`。清单中移除了极光的 `InitProvider`，因此进程启动时 SDK 不会自行初始化。
  - 极光 SDK 合并进来的权限中，推送用不到的一律从清单中移除：定位（含后台定位）、读取电话状态、查询全部应用、写外部存储。
- **推送标识（Registration ID）只属于一台设备**。同一部手机换账号登录时，标识转移到新设备，旧账号不再收到推送。设备下线或退出登录时，标识随之清除。
- **厂商通道**（华为、小米、OPPO、vivo、荣耀）需要各厂商的开发者账号和配置文件，在 v0.9.0 上线准备时接入。

### 6. 日历

- **App 内日历**：在备忘录模块中，与列表并列。
  - 提供月视图、两周视图和周视图，一周从哪天开始取用户设置。
  - 日期下方用标记区分备忘和工作日志。点按某天后显示当天的备忘和工作日志。
  - 宽屏时日历和日程左右并排。
- **系统日历（可选，按设备开启）**：
  - 在设置中开启后，App 才请求日历权限。
  - App 在本机账户下创建名为"即刻日志"的日历，单向写入备忘录：全天备忘写成全天事件，其余写成 30 分钟的事件。
  - 事件不带闹钟，避免和 App 自己的提醒重复。
  - 关闭时删除整个"即刻日志"日历。
  - 只写本机账户，不会随系统账户同步到云端。
  - 写入范围为过去 30 天到未来 1 年的备忘。
  - 备忘录 ID 和系统事件 ID 的对应关系保存在本地数据库中。

### 7. 设备时区：自己实现，不用 flutter_timezone（与预选不同）

本地提醒按 IANA 时区计算时刻。flutter_timezone 的 Android 构建脚本依赖 Kotlin 1.7 和 AGP 7.3，与本项目的 AGP 9 不匹配，构建时还要额外下载约 50MB 的编译器。它的功能只有一行：读取 `TimeZone.getDefault().id`。所以改在 `MainActivity` 中用平台通道 `jikelog/device` 自己实现。

## 后果

- **好处**：
  - 断网、App 被杀、服务端停机都不影响本机已同步的提醒。
  - 推送只在本地闹钟可能缺席时发送，既满足"App 推送"，也不会重复提醒。
  - 服务端只增加一张表和一个轮询循环。
- **代价**：
  - 备忘录的时间和提醒设置在服务端是明文。
  - 未开通极光的环境中，没有同步到备忘录的设备收不到提醒。验收时要用已同步的设备检查提醒。
- **待办**：
  - 厂商通道接入与推送到达率测试放到 v0.9.0。
  - 重复备忘（每天、每周）不在本期范围内，需求没有提出。
