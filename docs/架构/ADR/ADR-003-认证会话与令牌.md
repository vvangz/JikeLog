# ADR-003 认证会话与令牌

- 状态：已采纳
- 日期：2026-10-09

## 背景

需求要求支持用户名密码和手机号验证码两种登录方式，同时满足以下几点：

- 支持多设备同时登录，并能在"登录设备"里把某台设备下线
- 修改密码、找回密码后，其他设备要立即失效
- 手机端常处于弱网环境，刷新令牌的请求可能被重试，也可能有多个请求同时发起刷新

M1 初版用 Redis 记录"设备下线时间"，每个请求都检查一次。代码审查和安全审查都指出两个问题：

- 先提交数据库事务、再写 Redis 标记，如果中间失败，被下线设备的令牌在最长 15 分钟内仍然有效
- Redis 被清空或重启后，已下线的令牌会恢复有效

审查还指出：刷新令牌在宽限期内的重试会再换发一枚新令牌，导致客户端手里那枚令牌失效，用户被静默登出。

## 决策

1. **Access Token** 使用 HS256 JWT，有效期 15 分钟，载荷包含 `sub`（用户）、`sid`（设备会话）、`iat_ms`（毫秒级签发时间）和 `aud=app`。
   - 管理后台令牌使用不同的受众（aud），两类令牌不能互用。
   - 验签时依次尝试当前密钥和一把旧密钥，以便平滑轮换。令牌头不携带由密钥派生的标识。
2. **设备会话以数据库为准**。`devices` 表每行代表"某账号在某个安装实例上的登录"，新增 `tokens_valid_after` 字段，只接受签发时间不早于它的令牌。
   - 重新登录时把它更新为本次登录时刻，旧令牌随即作废。
   - 下线、修改密码时，在同一事务里更新它（同时设置 `revoked_at`）。
   - 认证中间件每个请求做一次主键查询。下线与业务事务同时生效，不依赖缓存。Redis 故障也不会影响已登录的请求。
3. **Refresh Token** 是 256 位随机串，数据库中只存它的 SHA-256。每次刷新都会轮换，并保留上一枚。
   - 出示当前那一枚：正常轮换。换发结果在 Redis 中缓存 30 秒，用出示的那枚令牌派生密钥（HKDF），以 AES-256-GCM 加密。
   - 30 秒内再次出示上一枚：直接返回缓存的同一结果，保证幂等，客户端无论保留哪次响应都有效。缓存丢失时退化为再换发一次，宽限期的起点不变。
   - 超过 30 秒后出示上一枚：视为令牌泄露，让该设备下线。
4. **默认拒绝**：除 `server/internal/server/public.go` 列出的公开路由外，所有路由都要求登录。测试会校验这份列表与 `openapi.yaml` 中标注 `security: []` 的接口完全一致。

## 备选方案

- **只用 Redis 记录下线状态**（初版）：每个请求开销最小，但上面列出的两个缺陷无法接受。
- **Access Token 不做逐请求校验，等它自然过期**：实现最简单，但"踢下线"要等最长 15 分钟才生效，不符合账号安全预期。
- **Refresh Token 不轮换**：令牌泄露后无法发现，也无从止损。

## 影响

- 每个已登录请求多一次主键查询，在同区域的 RDS 上约 0.3ms，对 p95 < 100ms 的目标影响可以忽略。v0.9.0 压测时如果成为瓶颈，再加进程内的短时缓存。
- Redis 现在只承担限流、验证码、注册凭证和刷新幂等缓存。Redis 不可用时，登录和发送验证码会失败，但已登录用户的正常使用不受影响。
