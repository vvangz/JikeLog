# ADR-005 同步协议：通用记录表 + 字段级时钟 + 文本补丁合并

- 状态：已采纳
- 日期：2026-10-09

## 背景

需求第 8 条要求多设备实时同步，冲突时"最后修改覆盖、版本合并"。另外：

- App 要离线可用：所有写入先落本地，联网后再上传
- 四个模块（工作日志、笔记、备忘录、记账）陆续上线，同步机制只能写一次
- 工作日志内容、笔记正文这类长文本，两台设备离线时各改一段很常见，整段覆盖会丢内容

## 决策

### 1. 服务端用一张通用记录表

所有同步实体存在 `records` 表中：

| 列 | 说明 |
|---|---|
| `id` | 客户端生成的 UUIDv7，全局唯一 |
| `user_id` / `entity` | 所属账号与实体类型（`worklog`、`attachment`……） |
| `fields` | JSONB，字段名 → 值；敏感字段存密文（见 ADR-006） |
| `clocks` | JSONB，字段名 → 该字段最后一次修改的 HLC |
| `version` | 每次写入 +1 |
| `server_seq` | 该账号内单调递增的序号，用于增量拉取 |
| `deleted` | 墓碑标记 |

每个实体的字段定义（类型、长度、是否必填、是否敏感、是否可合并、客户端是否可写）在 Go 代码里登记成 schema，推送时逐字段校验。新增模块只需登记 schema，同步引擎不用改。

`server_seq` 由 `sync_cursors` 表按账号分配：推送事务先锁住该账号的游标行，所以同一账号的推送是串行的，序号没有空洞和乱序。

### 2. 混合逻辑时钟（HLC）

客户端每修改一个字段，就给它打一个 HLC：`<13 位毫秒>-<4 位十六进制计数>-<16 位十六进制节点>`，按字符串比较就是先后顺序。节点取安装实例 ID 的哈希。客户端拉取到别的设备的时钟后会推进自己的时钟，所以即使手机时间略慢，新的修改也排在后面。

服务端拒绝物理时间比服务器快 5 分钟以上的时钟（`CLOCK_SKEW`），防止一台时间错乱的设备永远"赢"。

### 3. 推送：`POST /api/v1/sync/push`

每条变更只带**改过的字段**：

```json
{
  "entity": "worklog", "id": "…",
  "fields":     { "content": "新全文" },
  "clocks":     { "content": "1791553544038-0001-a1b2c3d4e5f60718" },
  "baseClocks": { "content": "1791550000000-0000-a1b2c3d4e5f60718" },
  "patches":    { "content": "[{\"p\":12,\"b\":\"上文\",\"d\":\"删除\",\"i\":\"插入\",\"a\":\"下文\"}]" }
}
```

补丁是一组片段（hunk）：`b` 和 `a` 是前后文，`d` 是删除的文本，`i` 是插入的文本，`p` 是该片段在基准文本中的字符位置，仅作定位提示。位置一律按 Unicode 码点计数，Go（`[]rune`）和 Dart（`runes`）两端一致。两端共用 `testdata/textpatch` 下的测试用例，保证结果相同。

没有直接使用 diff-match-patch 的补丁文本格式，原因是两端计位置的单位不同（Go 实现按字节或码点，Dart 按 UTF-16）。中文长文本里位置会偏出模糊匹配的范围，导致合并失败。

`baseClocks` 是客户端修改前、最后一次从服务端拿到的该字段时钟。服务端在事务内锁定记录后逐字段处理：

| 情况 | 处理 |
|---|---|
| 服务端时钟 = 客户端时钟 | 已经应用过（重试），跳过 |
| 服务端时钟 = `baseClocks` | 服务端在此期间没改过这个字段，直接采用客户端的值 |
| 两边都改过，字段可合并且带补丁 | 把客户端补丁（相对客户端的基准文本）应用到服务端当前文本上：在提示位置附近查找"前文 + 删除内容 + 后文"，找到就替换。所有片段都应用成功即为"版本合并"，结果为 `merged`；只要有一个片段找不到（对方改了同一处），就按下一行处理 |
| 两边都改过，其他情况 | **最后修改覆盖**：HLC 大的一方胜出。败方的值存入修订历史，结果为 `conflict`，客户端提示"存在冲突版本" |

- 删除是墓碑，删除胜过编辑。被删除记录上的编辑存入修订历史，可以恢复。
- 有字段被采纳时，`version` +1，并分配新的 `server_seq`。
- 结果为 `merged` 或 `conflict` 时，响应带回服务端的最终记录，客户端用它覆盖本地。
- 一批最多 100 条，请求体上限 4MB。单条校验失败只拒绝这一条（`rejected`），不影响同批其他变更。

选用补丁而不是三方合并，是因为补丁不需要服务端保存合并基准。客户端本来就保留着"最后同步的值"，用它生成补丁即可。

### 4. 拉取与确认

- `GET /api/v1/sync/pull?since=<seq>&limit=<n>`：按 `server_seq` 升序返回之后的全部记录，包括墓碑，同时返回 `nextSince` 和 `hasMore`。单页最多 500 条，并限制总字节数。
- 客户端处理完一页后调用 `POST /api/v1/sync/ack`，服务端记录到 `devices.last_ack_seq`。M4 的提醒去重要用它判断"这台设备是否已经同步到某条备忘录"。
- 客户端处理拉取结果时，未在本地修改过的字段直接采用服务端的值；本地已修改但还没推送的字段保留本地的值，只更新基准，下次推送时按上表合并。

### 5. 实时通知：`GET /api/v1/sync/ws`

- 写入事务提交后，向 Redis 频道 `sync:user:<id>` 发布 `{seq, origin}`。
- 每个 API 实例只订阅一次 `sync:user:*`，再转发给本实例上该账号的 WebSocket 连接。
- 客户端收到通知后发起拉取，`origin` 是自己的通知会被忽略。
- WebSocket 只用来提醒"有新数据"，不承载数据。丢一条通知也不会丢数据：App 回到前台、网络恢复时都会再拉一次。
- 连接期间服务端每分钟重新校验设备会话，设备被下线或改密后会主动断开（关闭码 4401）。

### 6. 修订历史

`record_revisions` 保存记录的历史状态，原因分三种：

- `edit`：同一设备 10 分钟内连续保存只留一份，避免自动保存产生大量版本
- `conflict`：冲突中落败的一方
- `delete`：删除前的最后状态

用户可以在 App 里查看历史版本，并恢复其中任意一个版本。恢复就是一次普通编辑，会正常同步到其他设备。

## 备选方案

- **每个模块一张业务表**：数据库约束更强，但每个模块都要写一遍推送、合并、拉取的代码，后续三个模块的工作量会成倍增加。最终选择通用表加 schema 校验。
- **整条记录 LWW**：实现最简单，但不满足"版本合并"的要求。两台设备分别改地点和内容时，后保存的一方会把另一方的修改覆盖掉。
- **服务端三方合并**：需要保存每个版本作为合并基准。现在由客户端用基准文本生成补丁，服务端只负责应用补丁。
- **CRDT（如 Yjs/Automerge）**：合并能力最强，但 Go 和 Dart 两端都缺成熟实现，存储也会膨胀。块级富文本合并到 M3 笔记时再评估。

## 影响

- 新模块只需在服务端登记 schema、在客户端定义视图模型，即可获得离线、同步、冲突处理和修订历史。
- 管理后台不读取 `records` 的内容，内容隔离由路由层保证（M7）。
- 服务端导出（M6）和提醒调度（M4）需要解析 `fields`，相关字段不能设为敏感字段，或者要在服务端解密后使用。
