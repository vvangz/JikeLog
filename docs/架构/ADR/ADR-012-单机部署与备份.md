# ADR-012 单机自托管部署、发布流程与 14 天加密备份

- 状态：已采纳
- 日期：2026-10-11

## 背景

M8 要把系统部署到正式环境，并落实需求第 10 条"数据备份周期为 14 日"。

实施计划原定使用阿里云托管服务（RDS、OSS、KMS、ACR）。2026-10-11 与用户确认后调整为：

- **部署**：沿用现有的阿里云 ECS（2 核、1.7G 内存、40G 磁盘），单机自托管，不使用 RDS、ACR、KMS。
- **域名**：`www.pingvv.top` 正在办理 ICP 备案。先把正式域名的部署全部做好，备案通过前继续用 SSH 隧道验收。
- **短信与推送**：暂不接入。只开放用户名加密码登录，提醒只依赖设备本地闹钟，代码中留好开关。
- **异地备份**：每 14 天一次，加密后上传到阿里云 OSS 另一地域的存储桶。

## 决策

### 1. 一台服务器、一个 Compose 项目

| 服务 | 镜像 | 说明 |
|---|---|---|
| caddy | caddy:2.10-alpine | 唯一对外的服务（80/443），自动申请 HTTPS 证书 |
| api | jikelog-api:<版本> | 接口与后台任务 |
| postgres | postgres:17-alpine | 数据卷 `pgdata` |
| redis | redis:7.4-alpine | 限流、验证码、实时通知；开启 AOF |
| objectstore | rustfs/rustfs:1.0.1 | 附件与导出文件（S3 兼容），不对外开放端口 |
| backup | jikelog-backup:<版本> | 每天检查一次，距上次成功备份满 14 天就执行 |

- 配置文件在仓库的 `deploy/production/`：`compose.yml`、`Caddyfile`、`.env.example`，以及运维脚本。
- 服务器上的部署目录为 `/root/jikelog`。
- 机密只存在服务器的 `.env` 中（权限 600），由 `init-env.sh` 生成随机值，包括数据库与 Redis 密码、JWT 密钥、传输加密私钥、本地主密钥、对象存储密钥。
- 异地 OSS 的 AccessKey 单独放在 `backup.env` 中，只提供给 backup 服务，接口服务读不到。
- 单机环境使用本地主密钥（`JIKELOG_KMS_PROVIDER=local`）。主密钥随加密备份一起保存，见第 4 节。

### 2. 一个域名承载全部入口

所有入口都在 `https://www.pingvv.top` 下，由 Caddy 分发：

| 路径 | 去向 |
|---|---|
| `/api/*`、`/healthz`、`/readyz` | api（含 WebSocket `/api/v1/sync/ws`） |
| `/admin/*` | 管理后台静态文件（单页应用，找不到的路径回到 `index.html`） |
| `/<存储桶>/*` | 对象存储（附件与导出文件的预签名上传和下载），只允许 GET、PUT、HEAD；响应一律作为下载（`Content-Disposition: attachment`，CSP `sandbox`），上传的 HTML 或 SVG 不会在本域名下执行 |
| `/` | 跳转到 `/admin/` |

- **对象存储走同一个域名**：
  - 预签名地址的签名包含主机名，因此对象存储的公开地址就是 `https://www.pingvv.top`，存储桶（默认 `jikelog`）作为路径的第一段（path-style）。
  - Caddy 原样转发 Host，签名校验能通过。
  - 不需要额外的子域名和证书。
- **管理后台与接口同源**：管理员的 Refresh Cookie 不跨站。
- **HTTPS 与安全响应头**：
  - 证书只向 Let's Encrypt 申请，不使用 Caddy 默认的备用签发机构。原因是 App 正式版只信任 Let's Encrypt 的根证书，见第 5 节。
  - 响应头开启 HSTS；管理后台另加 `frame-ancestors 'none'`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`。

### 3. 发布流程：GitHub Actions 构建，SSH 部署

- **触发**：Release Please 发布新版本后，或手动运行"部署"工作流时。
- **CI 中构建三样东西**：
  - API 镜像与备份镜像（linux/amd64）：导出为压缩包。服务器无法访问 Docker Hub，所以不走镜像仓库。
  - 管理后台：按 `/admin/` 路径构建。
- **通过 SSH 上传到服务器，执行 `deploy.sh <版本>`**：
  1. 先做一次部署前的数据库备份（保存在服务器本地，保留最近 5 份）。
  2. 载入镜像，执行数据库迁移。
  3. 更新镜像版本与管理后台文件，重启服务，等待就绪检查通过。
  4. 就绪检查不通过时，自动切回上一个版本的镜像与管理后台文件。数据库迁移只向前，需要回退时用部署前的备份恢复。
- **GitHub 中需要的配置**：
  - Secrets：`DEPLOY_HOST`、`DEPLOY_SSH_KEY`（专用的部署密钥）、`DEPLOY_KNOWN_HOSTS`，只放在 production 环境中。
  - 环境只允许 `main` 分支部署，并要求审批：部署密钥是服务器的 root 密钥。（v1.0.0 起去掉了原先允许的 `v*` 标签：从标签运行时工作流文件取自标签，能推送标签的人就能改写它。）
  - 手动输入的版本号经环境变量传入并按语义化版本校验，`deploy.sh` 也会再校验一次，防止命令注入。
  - Environment：`production`，可设置人工审批。

### 4. 每 14 天一次的加密全量备份

- **调度**：
  - backup 容器每天 03:30（北京时间）检查一次，距上次成功备份满 14 天就执行。
  - 不用"每月 1 日、15 日"这类日历规则，间隔才能始终是 14 天。
  - 也可以手动执行 `docker compose run --rm backup backup-now`。
- **备份内容**：
  - `db.dump`：PostgreSQL 全量（`pg_dump -Fc`）。
  - `objects/`：对象存储中的附件。导出文件 24 小时后就会删除，不备份。
  - `env`：服务器的 `.env`。数据库中的敏感字段由本地主密钥加密，没有主密钥，数据库备份就无法解开。
- **加密**：
  - 三个文件打包后用 [age](https://age-encryption.org/) 公钥加密，服务器上只有公钥。
  - 私钥由管理员离线保存（例如密码管理器），恢复时才用到。
  - 即使服务器被攻破、OSS 的密钥泄露，备份也打不开。
- **存放**：
  - 服务器本地保留最近 6 份。
  - 同时上传到另一地域的 OSS 存储桶（S3 兼容接口），由存储桶的生命周期规则在 90 天后删除，并开启版本控制。
  - 服务器上的 AccessKey 只有写入权限：服务器被攻破时，攻击者无法读取、删除或覆盖已有的异地备份。尚未配置 OSS 时只保留本地备份，并在日志中警告。
- **监控**：每次备份的结果写入 `backup/status.json`，`check-backup.sh` 在超过 15 天没有成功备份时返回非零（可接入监控）。
- **恢复**：
  - `restore.sh <备份文件>` 需要 age 私钥。
  - 默认是演练：把备份解密到临时目录，恢复到一个临时的 PostgreSQL 容器（不影响正式数据），校验各表行数与附件数后删除。
  - 加上 `--production` 才覆盖正式数据。
  - 各表行数在备份时从导出文件中统计，与导出是同一个快照，恢复后必须完全一致。
  - 恢复演练的步骤与记录见《部署运维 / 备份与恢复》。

### 5. App 正式版

- 接口地址为 `https://www.pingvv.top`。
- 正式版只信任 Let's Encrypt 的两个根证书（ISRG Root X1、X2），相当于把 CA 锁定。即使设备上装了其他 CA 证书（抓包工具、企业代理），也无法解密 App 的流量。
- 根证书文件随 App 打包，有效期到 2035 年及以后。如果 Let's Encrypt 启用新的根证书，需要发布新版 App。
- 调试版仍然信任系统证书，便于开发。

## 备选方案

- **阿里云托管服务（RDS、OSS、KMS、ACR）**：更可靠、运维更省心，但每月需额外支付数百元。用户选择单机自托管，以后可以平滑迁移：数据库迁移加 `pg_dump`、对象存储迁移，配置都在 `.env` 中。
- **把镜像推到 GitHub Container Registry，服务器拉取**：服务器访问境外镜像仓库不稳定，改为 CI 构建后直接上传压缩包。
- **用 `cron` 写"每 14 天"**：cron 的日期步长到月底会重置，间隔不总是 14 天。

## 影响

- **单点风险**：服务器损坏时，最多丢失上次备份之后的数据（最长 14 天）。部署前也会做一次备份。如需更短的恢复点，可以把备份间隔调小（环境变量 `BACKUP_INTERVAL_DAYS`），代价是 OSS 用量增加。
- **内存**：
  - 1.7G 内存运行全部服务：PostgreSQL 限制 `shared_buffers=128MB`，Redis 限制 `maxmemory 128MB`，另有 2G 交换分区。
  - 压测结果见 v0.9.0 开发日志。
- **用户需要完成的操作**：
  - ICP 备案。
  - 创建 OSS 存储桶与专用的 AccessKey。
  - 生成 age 密钥并离线保存私钥。
  - 在 GitHub 中配置部署用的 Secrets。
  - 步骤见《部署运维 / 生产部署》。
