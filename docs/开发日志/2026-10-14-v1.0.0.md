# 2026-10-14 · v1.0.0 · 正式发布

## 目标

实施计划中的最后一个里程碑：签名的正式 APK、文档定稿、Release Notes。

与用户确认的做法：

- 正式 APK 附在每个版本的 GitHub Release 上（仓库公开，任何人都能下载；App 只连接本项目的服务器）。
- 签名密钥由 Claude 在用户电脑上生成，用户负责离线备份。
- 附件暂不改存阿里云 OSS，每个账号的附件上限从 2GB 调到 8GB（2026-10-13 已在正式服务器生效）。

## 完成项

### 正式签名与发布 APK（`.github/workflows/release-apk.yml`）

- Release Please 创建 Release 后调用新的"发布 APK"工作流，与部署并行；也可以从 `main` 手动运行，为已发布的版本重新构建。
- 分两个任务，签名密钥不与仓库代码同处一台机器：
  - **构建**：没有密钥、只读权限。检出 `v<版本>` 标签，确认它指向的提交在 `main` 上，构建 release APK（Gradle 用调试密钥签名），作为产物交给下一步。
  - **签名并上传**：在 `apk-signing` 环境中运行，不检出仓库代码。用 `apksigner` 换成正式签名，核对证书 SHA-256 与仓库变量 `APK_CERT_SHA256` 一致后，上传 `jikelog-<版本>.apk` 与 `.sha256`。
- `versionCode` 由版本号推出（`1.2.3` → `10203`）；只为正式版本构建，次版本号与修订号不超过 99。
- GitHub 配置（已完成）：
  - 新建 `apk-signing` 环境，只允许 `main`，存放 keystore（base64）与 `key.properties`。两者都用 `gh secret set` 直接从文件读入。
  - 仓库变量 `APP_API_BASE`、`APP_E2E_PUBLIC_KEY`、`APK_CERT_SHA256`。
- 签名密钥：PKCS12、RSA 4096、有效期约 27 年，证书 SHA-256 `0B:34:89:42:…:BE:EE:73`。密码随机生成，直接写入文件，没有在终端或会话中显示。
- `build.gradle.kts`：本机构建时可以用 `key.properties`（路径由 `JIKELOG_KEY_PROPERTIES` 指定）正式签名；没有时仍用调试签名，便于 `flutter run --release`。

### 部署加固

- 解包发布包时加 `tar --no-same-owner`。CI 部署后，服务器上的 `scripts/`、`caddy/`、`compose.yml` 属于 uid 1001（GitHub 构建机的用户），root 执行的脚本不应归其他 uid 所有。服务器上已改回 root。
- `production` 与 `apk-signing` 环境都只允许 `main`，去掉了 `v*` 标签：从标签运行时，工作流文件取自标签，能推送标签的人就能改写它。
- 正式环境模板与 `init-env.sh` 中附件配额默认 8GB。
- 阿里云验证码与 KMS 的错误提示不再提"v0.9.0 接入"。

## v0.9.0 发布与部署中遇到的问题

v0.9.0 合并后，验收服务器迁移到正式结构，并第一次由 GitHub Actions 部署。下列问题都已解决：

| 问题 | 原因 | 解决 |
|---|---|---|
| 迁移时文档要求 `JIKELOG_ENV=production`，接口会拒绝启动 | 生产环境要求对象存储的公开地址为 https，备案前只能用 `http://127.0.0.1:9000` | 备案前用 `staging`（除 https 外检查相同），文档已改 |
| 首次备份上传 OSS 返回 403 | rclone 上传后 HEAD 校验需要读取权限，只能写入的 AccessKey 没有 | 加 `--s3-no-head`（v0.9.0 内修复） |
| 发布后的自动部署跳过了上传与部署，却显示成功 | 被调用的工作流读不到环境中的 Secrets，需要调用方写 `secrets: inherit` | PR #18：改回 `inherit`（仓库级 Secrets 为空）；读不到密钥时任务失败 |
| 手动部署报 `Load key: error in libcrypto` | `DEPLOY_SSH_KEY` 从 PowerShell 复制粘贴后无法读取 | 用 `gh secret set ... < 私钥文件` 重新设置；PR #20：写入前去掉 CR、校验私钥、先确认能登录 |
| 通过 SSH 管道执行脚本时，后半段没有执行 | `docker compose exec -T` 读走了经标准输入传来的后续命令 | 把脚本上传成文件再执行，标准输入接 `/dev/null` |

最终由"部署"工作流部署了 0.9.0（提交 ba0ab1b）。数据（1 个账号、46 条记录）、附件配额与备份配置都保留，首次异地备份已成功上传。

## 关键决策

- **签名放在单独的任务中**：Gradle 构建会执行仓库代码与第三方插件，不让它们与签名密钥同处一台机器。代价是多一次产物传递，以及 APK 先用调试密钥签名、再由 `apksigner` 替换（已在本机验证替换后只有一个签名者，且仍是 16KB 对齐）。
- **不加标签保护规则**：`main` 本身没有保护，有写权限的人本来就能修改部署与发布流程；只需保证密钥只交给从 `main` 运行的工作流。仓库只有一位维护者。
- **`apk-signing` 不要求审批**：签名不触及服务器，且证书指纹核对兜底；部署（`production`）仍要求审批。

## 审查记录

通用审查与安全审查都没有 CRITICAL。

| 级别 | 问题 | 处理 |
|---|---|---|
| HIGH（安全） | 写入 keystore 后才运行 Gradle 构建，仓库代码与插件能读到签名密钥；`apk-signing` 允许 `v*` 标签，从标签运行时工作流文件可被改写 | 构建与签名拆成两个任务；两个环境都只允许 `main`；构建前确认标签在 `main` 上 |
| HIGH（通用） | 《工作日志》使用说明仍写附件空间 2GB | 改为 8GB |
| MEDIUM（安全） | 构建任务拥有 `contents: write` | 构建任务只读，只有签名任务可写 |
| MEDIUM（通用） | 预发布版本与正式版本 versionCode 相同；带前导零的版本号会被当作八进制 | 只接受不带前导零的正式版本号 |
| MEDIUM（通用） | 已有服务器的 `.env` 不会自动补上 8GB 配额 | 正式服务器已手工设置；`deploy.sh` 不改 `.env` 中的其他项，以后升级会保留 |
| LOW | `key.properties` 缺少 `storeFile` 时报空指针 | 给出明确错误 |
| LOW（未处理） | 第一方 Action 用标签而非 SHA 固定；Gradle 依赖没有校验元数据 | 签名任务只用 download-artifact 与 setup-java 两个第一方 Action，且不运行仓库代码，影响很小 |
