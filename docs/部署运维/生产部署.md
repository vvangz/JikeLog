# 生产部署

正式环境是一台阿里云 ECS 上的单机 Docker Compose，所有入口都在 `https://www.pingvv.top` 下。设计与取舍见 [ADR-012](../架构/ADR/ADR-012-单机部署与备份.md)，备份见[《备份与恢复》](备份与恢复.md)，压测见[《压测》](压测.md)。

| 路径 | 内容 |
|---|---|
| `https://www.pingvv.top/` | 官网：产品介绍、下载、使用教程、更新日志、隐私政策（[ADR-014](../架构/ADR/ADR-014-官网与安装包下载.md)） |
| `https://www.pingvv.top/download/` | 安装包与下载清单 `latest.json` |
| `https://www.pingvv.top/api/` | 接口（含 WebSocket 实时通知） |
| `https://www.pingvv.top/admin/` | 管理后台 |
| `https://www.pingvv.top/<存储桶>/` | 附件与导出文件的预签名上传、下载 |

仓库中的部署文件：

| 文件 | 说明 |
|---|---|
| `deploy/production/compose.yml` | 全部服务：caddy、api、postgres、redis、objectstore、backup |
| `deploy/production/caddy/Caddyfile` | 域名、HTTPS、路径分发、安全响应头 |
| `deploy/production/.env.example` | 配置项说明（不要手工复制，用 `init-env.sh` 生成） |
| `deploy/production/scripts/` | `init-env.sh`（生成配置）、`deploy.sh`（部署）、`restore.sh`（恢复）、`check-backup.sh`（备份检查） |
| `deploy/production/tests/caddy-smoke.sh` | 用真实的 Caddy 检查 Caddyfile 的路由与响应头（CI 中运行，本机需要 Docker） |
| `deploy/backup/` | 备份镜像 |
| `.github/workflows/deploy.yml` | 构建镜像、管理后台与官网，收集 Release 中的安装包，经 SSH 上传并执行 `deploy.sh` |

服务器上的目录 `/root/jikelog`：

```
/root/jikelog
├── .env                 # 全部配置与机密（权限 600）
├── backup.env           # 异地 OSS 的 AccessKey，只提供给 backup 服务（权限 600）
├── compose.yml          # 每次部署时更新
├── compose.override.yml # 可选：本机的临时调整（部署不会覆盖），例如备案前的验收
├── caddy/Caddyfile      # 每次部署时更新
├── scripts/             # 每次部署时更新
├── admin/<版本>/         # 管理后台静态文件，admin/current 指向当前版本
├── site/<版本>/          # 官网静态文件，site/current 指向当前版本
├── downloads/<版本>/     # 安装包与 latest.json，downloads/current 指向最新的一个有安装包的版本
├── releases/<版本>/      # 上传的发布包，保留最近 3 个
└── backups/             # 加密备份、状态，以及 predeploy/ 中部署前的数据库备份
```

## 1. 一次性准备（需要你完成）

### 1.1 域名与备案

- `www.pingvv.top` 与 `pingvv.top` 的 A 记录指向服务器公网 IP。
- ICP 备案号：冀ICP备2026046562号-1（2026-10-23 通过），填在仓库变量 `SITE_ICP` 中。
- 阿里云 ECS 安全组的入方向须放行 TCP 80 与 443（HTTP/3 另需 UDP 443）。
- 备案通过之前，阿里云会拦截这两个域名的 80/443 访问，此时按[第 5 节](#5-备案通过前的验收)经 SSH 隧道验收。

### 1.2 备份加密密钥（age）

在自己的电脑上生成，私钥离线保存（例如密码管理器），**不要放到服务器上**：

```bash
# 没有安装 age 时，可以借用备份镜像：docker run --rm --entrypoint age-keygen jikelog-backup:<版本>
age-keygen -o jikelog-backup.key
# 输出中 "Public key: age1…" 就是公钥，填到服务器 .env 的 BACKUP_AGE_RECIPIENT
```

丢失私钥意味着所有备份都无法解开。

### 1.3 异地 OSS 存储桶

1. 在**与服务器不同的地域**创建一个私有存储桶，例如华东 2（上海）的 `jikelog-backup-<随机后缀>`。
2. 在存储桶上设置：
   - **生命周期规则**：前缀 `jikelog-`，上传 90 天后删除（相当于保留最近 6 份）。
   - **版本控制**：开启。即使有人用同名文件覆盖，旧版本仍在。
3. 在 RAM 中创建一个只用于备份的用户，**只授予写入权限**（把 `<存储桶>` 换成实际名称）。服务器被攻破时，攻击者也无法读取、列出或删除已有的备份：

   ```json
   {
     "Version": "1",
     "Statement": [
       {
         "Effect": "Allow",
         "Action": ["oss:PutObject"],
         "Resource": ["acs:oss:*:*:<存储桶>/jikelog-*"]
       }
     ]
   }
   ```

4. 为该用户创建 AccessKey，填到服务器的 `backup.env`（不是 `.env`，接口服务读不到它）：

   ```
   BACKUP_OSS_ENDPOINT=https://oss-cn-shanghai.aliyuncs.com
   BACKUP_OSS_BUCKET=<存储桶>
   BACKUP_OSS_ACCESS_KEY_ID=<AccessKey ID>
   BACKUP_OSS_ACCESS_KEY_SECRET=<AccessKey Secret>
   ```

   旧备份由生命周期规则删除。如果改为由备份脚本删除，在 `.env` 中设置 `BACKUP_OSS_PRUNE=true`，并给 AccessKey 加上 `oss:ListObjects` 与 `oss:DeleteObject`。

### 1.4 GitHub 部署配置

1. 生成部署专用的 SSH 密钥，公钥加到服务器 `/root/.ssh/authorized_keys`：

   ```bash
   ssh-keygen -t ed25519 -C jikelog-github-deploy -f jikelog-github-deploy -N ""
   ssh-copy-id -i jikelog-github-deploy.pub root@<服务器 IP>
   ssh-keyscan -t ed25519 <服务器 IP>      # 输出用于 DEPLOY_KNOWN_HOSTS
   ```

2. 仓库 Settings → Environments → 新建 `production`：
   - **Required reviewers**：勾选自己，每次部署前需要你批准。
   - **Deployment branches and tags**：选 Selected，只允许 `main` 分支（不要加 `v*` 标签）。否则任何能推送分支或标签的人都可以改工作流、拿到服务器的 root 密钥。
   - 添加下面三个 **Environment secrets**（不要放在仓库级 Secrets 中）：

   | Secret | 值 |
   |---|---|
   | `DEPLOY_HOST` | 服务器公网 IP |
   | `DEPLOY_SSH_KEY` | `jikelog-github-deploy` 私钥的全部内容 |
   | `DEPLOY_KNOWN_HOSTS` | `ssh-keyscan` 的输出 |

   建议用命令设置，避免从终端复制粘贴时混入 Windows 换行符（部署时报 `error in libcrypto`）：

   ```bash
   gh secret set DEPLOY_SSH_KEY --env production < jikelog-github-deploy
   ```

   读不到 `DEPLOY_HOST` 时部署任务失败，发布包保存为 Actions 产物（7 天）。Release Please 调用部署工作流时须写 `secrets: inherit`，否则被调用的工作流读不到环境中的 Secrets。

3. **仓库变量**（Settings → Secrets and variables → Actions → Variables）：
   - `SITE_ICP`：ICP 备案号，如 `京ICP备2026000000号-1`。备案通过后设置，官网页脚随之显示并链接到工信部网站；未设置时不显示。
   - `APK_CERT_SHA256`、`WINDOWS_CERT_THUMBPRINT`：已在[《发布 APK》](发布APK.md)、[《发布 Windows 版》](发布Windows版.md)中设置。部署时用它们再核对一次 Release 中安装包的签名证书，不符时部署失败。

### 1.5 官网与安装包下载

发布新版本时，Release Please 等 APK 与 Windows 安装包上传到 Release 后才调用部署（安装包构建失败时照常部署）。部署工作流：

1. 在不带 production 环境的"官网与安装包"任务中构建官网（`apps/site`，使用教程、更新日志与法律文本由 `docs/` 生成）。
2. 同一任务中运行 `scripts/collect-downloads.sh`：从这个版本的 Release 下载 `jikelog-<版本>.apk`、`.msix`、`.sha256` 与 `jikelog-windows.cer`，与签名任务输出的校验值、APK 的签名证书、Windows 证书的指纹逐一核对，生成 `latest.json`。任何一项不符时部署失败。
3. 部署任务把它们与其他发布包一起上传，由 `deploy.sh` 解压到 `site/<版本>/` 与 `downloads/<版本>/`，再切换 `current`。

Release 中没有安装包时（例如手动重新部署一个旧版本），官网下载页保持上一个版本；手动部署时没有签名任务的校验值，只核对 `.sha256` 与签名证书。官网上线之前的版本没有 `apps/site`，只部署程序。官网的下载页读不到 `latest.json` 时，改为引导到 GitHub Release 下载。

法律文本（`docs/法律/`）中还有【待填写】时，构建会在运行摘要中给出警告，页面顶部显示"草稿"。

### 1.6 短信登录（阿里云）

个人实名的阿里云账号不能用普通的"短信服务"：自定义签名无法通过实名制报备。因此改用**号码认证服务的"短信认证"**，它提供系统赠送的签名与模板，不需要审核。验证码由接口服务生成并自行校验，阿里云只负责下发。发送登录、找回密码验证码前，还要先通过**验证码 2.0** 的人机验证（生产环境的配置校验要求两者同时开启）。

1. 号码认证服务控制台 → 短信认证：开通并购买短信认证套餐包（不能使用普通短信服务的余额）。在"参数配置"中记下赠送签名的名称；赠送模板的编号与默认值（100001 / 100003 / 100004 / 100005）一致时不需要另外配置。
2. 验证码 2.0 控制台：新建场景，客户端选 Web/H5，记下场景 ID 与身份标。
3. RAM：新建只允许 OpenAPI 调用的用户，授予只包含 `dypns:SendSmsVerifyCode` 与验证码校验权限的自定义策略，并用 `acs:SourceIp` 条件限制为服务器的公网 IP。
4. 在服务器的 `.env` 中设置：

   ```
   JIKELOG_SMS_PROVIDER=aliyun
   JIKELOG_SMS_SIGN_NAME=<赠送签名>
   JIKELOG_CAPTCHA_PROVIDER=aliyun
   JIKELOG_CAPTCHA_SCENE_ID=<场景 ID>
   JIKELOG_CAPTCHA_PREFIX=<身份标>
   JIKELOG_ALIYUN_ACCESS_KEY_ID=<AccessKey ID>
   JIKELOG_ALIYUN_ACCESS_KEY_SECRET=<AccessKey Secret>
   ```

   然后执行 `docker compose up -d api`。系统信息（`/api/v1/system/info`）中的 `features.sms` 变为 `true`、`features.captcha` 给出场景参数后，App 会显示验证码登录与找回密码。

- 发送失败时，接口日志中有 `sms send failed`，附阿里云返回的错误码与 RequestId。常见原因：`Forbidden.*`（RAM 权限不足或服务未开通）、套餐包用完、`MOBILE_NUMBER_ILLEGAL`（号码无效，App 提示"该手机号无法接收短信"）。
- 阿里云对同一号码的天级或频次限制（`BUSINESS_LIMIT_CONTROL`、`FREQUENCY_FAIL`）按"发送过于频繁"返回给 App。接口服务自己的限制是：同一号码 60 秒冷却、每天 10 条；同一 IP 每小时 20 条。
- 每个 IP 每小时最多提交 60 次人机验证（每次校验都调用阿里云）。校验时网络不通或阿里云服务端出错（5xx），按阿里云的容灾建议放行，但全服务每分钟最多放行 20 次，日志中有 `captcha verify unavailable, failing open`；超出时拒绝并记录 `fail-open budget exhausted`。限流（429）、鉴权失败等配置错误与无法解析的响应不放行，发送验证码返回 500。
- 已登录后发送验证码（绑定、换绑手机号，用验证码改密码或注销）同样需要人机验证。Windows 版没有内嵌网页组件，开启人机验证后这些操作与验证码登录都不可用，只能用密码，界面会提示到手机上操作。
- 开通前确认隐私政策已说明短信与人机验证的第三方处理，App 的隐私政策版本号已递增。

## 2. 首次部署

### 2.1 生成配置

把仓库中的 `deploy/production/scripts/init-env.sh` 复制到服务器后执行：

```bash
mkdir -p /root/jikelog/scripts && cd /root/jikelog
# scp deploy/production/scripts/init-env.sh root@<服务器 IP>:/root/jikelog/scripts/
bash scripts/init-env.sh www.pingvv.top <证书联系邮箱>
```

- 所有机密都是随机生成的，只写入 `.env` 与 `backup.env`（权限 600）。
- 终端会输出 App 构建需要的传输加密公钥（`--dart-define=JIKELOG_E2E_PUBLIC_KEY=…`），记下来。
- 然后在 `.env` 中填上 `BACKUP_AGE_RECIPIENT`，在 `backup.env` 中填上 OSS 的四项。
- 域名必须以 `www.` 开头：不带 `www` 的域名会跳转到它。证书联系邮箱不能为空，否则 Caddy 无法启动，部署脚本也会拒绝执行。

`init-env.sh` 可以重复执行：已有的值一律保留，只补上缺少的项。

### 2.2 部署

在 GitHub 的 Actions 页面手动运行"部署"工作流，版本留空即部署 `version.txt` 中的版本。之后每次 Release Please 发布新版本都会自动部署。

部署脚本 `deploy.sh <版本>` 依次执行：

1. 检查版本号与必填配置（`ACME_EMAIL`、`SITE_DOMAIN`）。
2. 部署前备份数据库到 `backups/predeploy/`（保留最近 5 份）。
3. 载入镜像（工作流会一并上传服务器缺少的第三方镜像），更新 `compose.yml`、Caddyfile、脚本和管理后台。
4. 数据库迁移。
5. 启动服务，重新加载 Caddy，等待就绪检查。
6. 失败时自动切回上一个版本的镜像、`compose.yml`、Caddyfile 和管理后台。
7. 成功后清理旧版本：发布包、管理后台和镜像各保留最近 3 个版本。

### 2.3 创建超级管理员

见[《管理员手册》](../管理员手册.md)第 1 节。

### 2.4 App 正式版

正式签名的 APK 在每次发布时由 GitHub Actions 构建并附到 Release，签名密钥与构建参数的配置见[《发布 APK》](发布APK.md)。把 2.1 中输出的公钥填到仓库变量 `APP_E2E_PUBLIC_KEY`。

- 正式版只信任 Let's Encrypt 的根证书（ISRG Root X1、X2）。服务器改用其他证书颁发机构之前，必须先发布新版 App。
- 临时关闭锁定（排查用，本机构建时）：加 `--dart-define=JIKELOG_PIN_CA=false`。

## 3. 日常运维

所有命令都在 `/root/jikelog` 下执行。

| 操作 | 命令 |
|---|---|
| 查看状态 | `docker compose ps` |
| 查看接口日志 | `docker compose logs -f --tail 200 api` |
| 重启某个服务 | `docker compose restart api` |
| 重新部署已上传的版本 | `bash scripts/deploy.sh <版本>`（`releases/<版本>/` 必须还在） |
| 部署其他版本 | 在 Actions 中运行"部署"工作流并填写版本 |
| 修改 `.env` 或 `backup.env` 后生效 | `docker compose up -d --force-recreate api backup` |
| 立即备份 | `docker compose run --rm backup backup-now` |
| 检查备份是否按时完成 | `bash scripts/check-backup.sh` |
| 进入数据库 | `docker compose exec postgres psql -U jikelog` |

### 回滚

- **只回退程序**：重新部署上一个版本（`bash scripts/deploy.sh <上一个版本>`）。前提是新版本没有做不兼容的数据库迁移。官网与下载页一起切回（发布包中有 `site.tar.gz`、`downloads.tar.gz` 时）。
- **连数据一起回退**：数据库迁移只向前。用 `backups/predeploy/` 中部署前的备份恢复：

  ```bash
  docker compose stop api backup
  docker compose exec -T postgres pg_restore -U jikelog -d jikelog --clean --if-exists --no-owner \
    < backups/predeploy/db-before-<版本>-<时间>.dump
  bash scripts/deploy.sh <上一个版本>
  ```

  部署之后写入的数据会丢失。

### 证书

Caddy 自动申请和续期 Let's Encrypt 证书，保存在 `caddy_data` 卷中。不要删除这个卷：Let's Encrypt 对同一域名每周的签发次数有限制。

### 资源

1.7G 内存运行全部服务，另有 2G 交换分区。PostgreSQL 的 `shared_buffers` 为 128MB、Redis 最多 128MB，压测时的占用见[《压测》](压测.md)。

附件存在本机硬盘（`objdata` 卷）上，每个账号上限由 `JIKELOG_ATTACHMENT_QUOTA` 决定（默认 8GB）。这是上限而不是预留：用户增多后用 `df -h /` 关注磁盘余量，不够时扩容云盘，或把附件改存阿里云 OSS（App 需要同时信任 OSS 域名的证书，须在发布新版 App 时一并修改）。

## 4. 从验收环境迁移

2026-10-09 起服务器上运行的是验收环境（`/root/jikelog`，Compose 项目同为 `jikelog`）。正式部署使用相同的项目名和卷名，数据库、附件和已申请的证书都会保留。

迁移步骤：

```bash
cd /root/jikelog
cp .env .env.bak-v0.8.0 && cp compose.yml compose.yml.bak-v0.8.0
# 1. 解出新版脚本（发布包已上传到 releases/<版本>/）
tar --no-same-owner -xzf releases/<版本>/config.tar.gz scripts
# 2. 补上缺少的配置项（已有的值保留）
bash scripts/init-env.sh www.pingvv.top <证书联系邮箱>
# 3. 手工修改验收环境遗留的值（见下表）
# 4. 部署
bash scripts/deploy.sh <版本>
```

| 配置 | 验收环境 | 正式环境 |
|---|---|---|
| `JIKELOG_ENV` | `development` | 备案通过前 `staging`，之后 `production`（生产环境要求对象存储的公开地址为 https） |
| `JIKELOG_SMS_PROVIDER` | `mock` | `disabled` |
| `JIKELOG_LOG_FORMAT` | `text` | `json` |
| `JIKELOG_STORAGE_PUBLIC_ENDPOINT` | `http://127.0.0.1:9000` | `https://www.pingvv.top`（备案通过之后再改，见第 5 节） |

- 验收环境的 `.env` 中没有 `JIKELOG_VERSION`，部署脚本因此没有可以自动切回的版本。迁移失败时，用上面备份的两个文件恢复，再执行 `docker compose up -d`。
- 旧的 `Caddyfile`、`deploy_m2.sh` 和镜像压缩包不再使用，确认正常后可以删除。

## 5. 备案通过前的验收

备案通过前，外网无法访问域名，App 与管理后台经 SSH 隧道访问服务器。

1. 在服务器上新建 `compose.override.yml`，让对象存储在本机开放端口（部署不会覆盖这个文件）：

   ```yaml
   services:
     objectstore:
       ports: ["127.0.0.1:9000:9000"]
   ```

   并保持 `.env` 中 `JIKELOG_STORAGE_PUBLIC_ENDPOINT=http://127.0.0.1:9000`，然后 `docker compose up -d`。

2. 在电脑上建立隧道，再把手机的端口转发到电脑：

   ```bash
   ssh -N -L 8080:127.0.0.1:8080 -L 9000:127.0.0.1:9000 root@<服务器 IP>
   adb reverse tcp:8080 tcp:8080 && adb reverse tcp:9000 tcp:9000
   ```

3. App 使用 `--dart-define=JIKELOG_API_BASE=http://127.0.0.1:8080` 构建（HTTP 地址不做证书锁定）。
4. 管理后台：在电脑上 `cd apps/admin-web && pnpm build && pnpm preview`，打开 `http://127.0.0.1:4173`。
